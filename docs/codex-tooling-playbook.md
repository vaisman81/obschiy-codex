# Codex Tooling Playbook

Цель: меньше тратить токены в чате и больше проверять локально. Codex должен сначала использовать локальные инструменты, а в ответ писать только итог, важные ошибки и следующие действия.

## Основной принцип

Не пересказывать большие файлы и логи в чат. Вместо этого:

1. Найти нужные файлы быстрым поиском.
2. Прочитать только релевантные фрагменты.
3. Запустить локальную проверку.
4. Вернуть короткий вывод: что сделано, чем проверено, что осталось.

## Быстрый поиск

Использовать:

```powershell
rg "строка или функция"
rg --files
fd имя_файла
```

Когда применять:

- найти функцию, класс, API endpoint, текст ошибки;
- понять структуру проекта;
- не открывать весь репозиторий целиком.

Зачем экономит токены:

- Codex читает только найденные места, а не большие файлы целиком.

## Git

Использовать:

```powershell
git status --short --branch
git diff -- файл
git log --oneline -5
git add файл
git commit -m "message"
git push
```

Когда применять:

- перед изменениями проверить рабочее дерево;
- после изменений показать точный diff;
- фиксировать готовые шаги маленькими коммитами.

Правило:

- не делать широкий `git add .`, если в проекте есть артефакты или секреты;
- сначала проверить `.gitignore` и `git status`.

## Pre-commit

Использовать:

```powershell
pre-commit run --all-files
pre-commit install
```

Когда применять:

- перед коммитом;
- после правок форматирования, Dockerfile, YAML/JSON;
- если нужно быстро поймать мелкие ошибки.

Зачем экономит токены:

- не обсуждать пробелы, переносы строк, конфликтные маркеры и Dockerfile-ошибки в чате.

## Docker

Использовать:

```powershell
docker info
docker compose config
docker compose up -d --build
docker compose ps
docker compose logs --tail 80 app
docker compose down
```

Когда применять:

- проверить, что приложение реально стартует;
- воспроизвести окружение на другом компьютере;
- проверить контейнеры вместо ручной настройки сервисов.

Правило:

- сначала `docker compose config`, потом `docker compose up`;
- логи читать коротко: `--tail 80`, не тащить весь лог в чат.

## Python

Использовать:

```powershell
python --version
python -m pip --version
python -m py_compile файл.py
python -m pip install -r requirements.txt
```

Когда применять:

- для Python-скриптов и backend;
- после изменения `.py` минимум запускать `py_compile`;
- если есть тесты, запускать тесты.

## Node.js

Использовать:

```powershell
node --version
npm --version
node --check файл.mjs
npm test
npm run build
```

Когда применять:

- для `.js`, `.mjs`, frontend и утилит;
- минимум `node --check` для измененного JS/MJS-файла.

## JSON, YAML и текстовые данные

Использовать:

```powershell
jq . file.json
yq . file.yml
sd "старое" "новое" файл
```

Когда применять:

- проверять JSON/YAML без вставки содержимого в чат;
- делать точечные замены;
- быстро смотреть структуру данных.

## Безопасность

Использовать:

```powershell
trivy fs .
trivy image имя_образа
hadolint Dockerfile
shellcheck script.sh
```

Когда применять:

- перед публикацией Docker-образов;
- после изменения Dockerfile;
- для shell-скриптов на macOS/Linux.

Правило:

- секреты не коммитить;
- `.env`, `*.conf`, ключи, токены и cookies должны быть в `.gitignore`.

## GitHub CLI

Использовать:

```powershell
gh auth status
gh auth login
gh pr create
gh pr view --web
```

Когда применять:

- создать PR без ручного копирования;
- проверить авторизацию;
- открыть PR в браузере.

## Bootstrap на Windows

На новом Windows-компьютере основной вход:

```cmd
bootstrap\windows\bootstrap.cmd
```

Для безопасной проверки без установки:

```cmd
bootstrap\windows\bootstrap.cmd -SkipInstall -SkipDocker -SkipAuth
```

Что делает:

- ставит инструменты;
- обновляет репозиторий;
- проверяет GitHub auth;
- включает pre-commit;
- проверяет Docker.

## Что писать пользователю

Плохо:

- вставлять длинные логи целиком;
- пересказывать весь файл;
- долго объяснять очевидные команды.

Хорошо:

- `Сделано: ...`
- `Проверено: команда -> итог`
- `Осталось: ...`

Пример короткого отчета:

```text
Сделано: обновил Dockerfile и compose.
Проверено: docker compose config, docker compose up -d --build, HTTP 200 на /.
Осталось: нет критичных рисков.
```

## Минимальный чеклист перед финальным ответом

1. `git status --short`
2. релевантный тест или проверка
3. короткий итог без больших логов
4. если были изменения: точные файлы и команды проверки
